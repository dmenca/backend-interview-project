# 锁按粒度区分
## 表级锁

作用范围：整个表

优点：
- 开销小
- 加锁块
- 没有死锁

缺点：
- 锁粒度大、并发能力差

```sql
LOCK TABLE t READ;
LOCK TABLE t WRITE;
UNLOCK TABLES;
```
MyISAM仅支持表锁，InnoDB支持表锁和行锁

## 行级锁
作用范围：某一行或某一范围

优点：
- 锁粒度小
- 并发度高

缺点：
- 加锁慢
- 开销大
- 可能出现死锁

# 锁的模式区分
## 共享锁（S锁 Shared Lock）
- 称为读锁，多个事务可以同时加S锁，允许读但是禁止写
- 会话 A 给行加 S 锁后，会话 B 可以加 S 锁（一起读），但不能加 X 锁（写），直到 A 释放 S 锁。
```sql
SELECT ... LOCK IN SHARE MODE
```

## 排他锁（X锁）
- 称为写锁，独占锁资源，禁止其他任何锁（包括 S 锁和 X 锁）。
- 会话 A 给行加 X 锁后，会话 B 既不能读（加 S 锁）也不能写（加 X 锁），直到 A 提交 / 回滚事务释放锁。

```sql
SELECT ... FOR UPDATE
```

# 锁按状态分
## 乐观锁
假设并发不会冲突，不加锁，只在更新时检查数据是否被修改（比如通过版本号 / 时间戳）。
示例（版本号实现）：

```sql
-- 表结构：id, name, version
UPDATE user SET name='张三', version=version+1 WHERE id=1 AND version=1; -- 只有version匹配才更新，否则说明被其他会话修改过
```

## 悲观锁
假设并发一定会冲突，强制加锁（比如行锁、表锁），是 MySQL 默认的锁策略（InnoDB 行锁）。

# InnoDB的包含的锁类型
InnoDB的行锁、间隙锁、临键锁（Next-key lock）是实现并发控制和事务隔离级别的核心锁机制。

## 行锁（Record Lock）
1. 核心定义
行锁是InnoDB最基础的行级锁，锁定的是表中具体的索引记录（不是物理行），只有通过索引定位到的行也会被加锁。
其中包括共享锁和排他锁。
* 共享锁（S锁）：通过select  .... lock in share mode 手动加锁，允许你并发读，禁止写。  
* **排他锁（X锁）**：通过select ...FOR UPDATE 手动加锁，**INSERT/UPDATE/DELETE会自动加锁**，独占资源，禁止并发操作。

**普通的select语句是快照读不会加行锁。**

2. 实现原理

InnoDB行锁的实现依赖索引：
* 如果查询条件使用主键索引或唯一索引，InnoDB会直接锁定对应的索引记录，仅影响目标行。
* 如果查询条件使用普通索引，InnoDB会先锁定普通索引记录，再锁定对应的主键索引记录。（回表时加锁）
* 如果查询条件无索引，行锁会退化成表锁。（InnoDB需扫描全表，锁定所有行）

3. 注意事项

行锁的释放时机：事务提交（COMMIT）或回滚（ROLLBACK）后。

## 间隙锁（Gap Lock）
1. 核心定义

**间隙锁是为了拒绝幻读问题引入的锁。** 锁定的是两个索引记录之间的间隙（即不存在的记录区间），而非具体的行。间隙锁的目的是**为了阻止其他事务再间隙中插入新数据**，避免同一事务两次查询同一范围时结果集行数变化。（幻读）

2. 使用场景

* InnoDB默认级别（可重复读）下生效
* 当查询条件为范围查询（ > 、< 、 between）且使用非唯一索引时，InnoDB会自动添加间隙锁。
* 若查询条件使用唯一索引（如主键），间隙锁会自动失效，退化为行锁（因为唯一索引的范围是确定的，无需锁定间隙）。


3. 间隙的判定规则

间隙是指**索引记录之间的区间**，包括
* 表中第一条记录之前的区间（如id<1）
* 两条相邻记录之间的区间（id=1和id=3之间区间（1,3））
* 表中最后一条记录之后的区间（如id>5）
间隙包括：(-∞,1)、(1,3)、(3,5)、(5,+∞)

4. 示例（范围查询触发间隙锁）

事务A
```sql
 select * from users where id >3 and id<11 for update; 
```
Innodb会对以下资源加锁：
* 对id=8的行加行锁（X锁）
* 对区间（3,8）、（8,11）加间隙锁

事务B
```sql
insert into users(id,name,status) values (6,'laoba',1); --- 比间隙锁（3,8）阻塞
INSERT INTO user(id, name,status) VALUES(10, 'laoshi'); --- 被阻塞（插入到间隙 (8,11)）。
UPDATE user SET name='李四2' WHERE id=8；--- 被阻塞（行锁互斥）。
```

5. 关键注意事项
* 间隙锁不阻止读操作，仅阻止插入操作。
* 间隙锁的释放时机：事务提交或回滚后。

## 临键锁（Next-key Lock）
**1. 核心定义**

临键锁是InnoDB**行锁和间隙锁的组合**，锁定的是一个索引记录以及间隙。临键锁是 InnoDB 在可重复读隔离级别下的默认锁类型，当执行范围查询时，InnoDB 会自动使用临键锁来防止幻读。

**2. 临键锁的构成**
临键锁 = 行锁（Record Lock） + 间隙锁（Gap Lock）
例如，对 id > 2 AND id < 5 加临键锁，实际锁定的是：
* 间隙 (1,3)（间隙锁）。
* 行 id=3（行锁）。
* 间隙 (3,5)（间隙锁）。

**3. 临键锁的左闭右开原则**

InnoDB 的临键锁遵循左闭右开的区间规则，即锁定的区间为 [a, b)。以上述 user 表为例，临键锁的区间包括：
(-∞,1]、(1,3]、(3,5]、(5,+∞)

**4. 示例（临键锁的默认触发）**
事务 A：
```sql
BEGIN;
SELECT * FROM user WHERE id <= 3 FOR UPDATE; -- 范围查询
```
InnoDB 会自动加临键锁，锁定区间 (-∞,3]，即：
* 间隙 (-∞,1)（间隙锁）。
* 行 id=1（行锁）。
* 间隙 (1,3)（间隙锁）。
* 行 id=3（行锁）。

**5. 临键锁的退化场景**

临键锁在以下场景会退化为行锁或间隙锁：
* 使用唯一索引查询单个记录：如 SELECT * FROM user WHERE id=3 FOR UPDATE;（主键索引），临键锁退化为行锁（仅锁定 id=3）。
* 隔离级别为读已提交：临键锁退化为行锁（间隙锁失效）。
* 查询条件为不存在的记录：如 SELECT * FROM user WHERE id=4 FOR UPDATE;，临键锁退化为间隙锁（仅锁定 (3,5)）。

## 实战关键要点

1. 临键锁是默认锁类型：在可重复读隔离级别下，InnoDB 对所有范围查询都会自动加临键锁，无需手动操作。

2. 唯一索引是关键：使用主键或唯一索引查询单条记录时，临键锁会退化为行锁，避免不必要的间隙锁定，提高并发性能。

3. 隔离级别影响锁行为：
* 可重复读（默认）：支持行锁、间隙锁、临键锁，彻底解决幻读。
* 读已提交：仅支持行锁，间隙锁和临键锁失效，可能出现幻读，但并发性能更高。

4.行锁失效的核心原因： 查询条件未使用索引，导致行锁退化为表锁，需确保查询条件使用有效索引。
