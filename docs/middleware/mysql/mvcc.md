**事务的 MVCC：InnoDB 并发控制的核心**

MVCC（Multi-Version Concurrency Control，多版本并发控制）是 InnoDB 实现高并发读写的核心机制,本质是为每行数据维护多个版本，让读操作（快照读）可以访问数据的历史版本，避免与写操作互斥阻塞，同时保证事务隔离级别（尤其是可重复读）。

简单来说：MVCC 就是 “给数据拍快照”，读操作拿历史快照，写操作改新版本，读写互不干扰，既保证了一致性，又提升了并发性能。

## 1. MVCC 的核心目标
解决传统锁机制的痛点：
* 悲观锁（行锁 / 表锁）下，读会阻塞写、写会阻塞读，并发性能低；
* 单纯的锁机制无法高效实现 “可重复读” 隔离级别（避免不可重复读、幻读）。
MVCC 的核心优势：读不阻塞写，写不阻塞读（快照读场景），兼顾一致性和并发性能。

## 2、MVCC 的核心组件（InnoDB 底层支撑）
MVCC 的实现依赖 3 个关键结构，缺一不可：

**1. 隐藏列（每行数据的版本元数据）**

InnoDB 会为表中每行数据（除用户定义字段外）自动添加 3 个隐藏列：

|隐藏列|作用|
|--|--|
|DB_TRX_ID|	最后一次修改该行数据的事务 ID（事务唯一递增，由 InnoDB 分配）|
|DB_ROLL_PTR|回滚指针，指向 undo log 中该行的历史版本（形成版本链）|
|DB_ROW_ID|聚簇索引无主键时的默认行 ID（可选，有主键则用主键）|

示例：用户表user(id, name)的实际存储结构（简化）：

|id|	name|	DB_TRX_ID|	DB_ROLL_PTR|
|--|--|--|--|
|1|	张三|	100|	指向 undo log 版本 99|
|2|	李四|	101	|指向 undo log 版本 100|

**2.Undo Log（回滚日志)**
* 作用：存储数据的历史版本，由DB_ROLL_PTR串联成 "版本链"
* 生成时机：事务修改数据时，先将旧版本写入 undo log，再更新当前行
* 版本链：每行数据的多个版本通过DB_ROLL_PTR按时间倒序链接（最新版本在表中，历史版本在 undo log）

```
当前行（DB_TRX_ID=102） → undo log版本101（DB_TRX_ID=100） → undo log版本99（初始版本）
```

**3. Read View（读视图）**
** 作用：事务执行快照读时，生成一个 “可见性规则”，判断版本链中哪个版本对当前事务可见；
** 生成时机：
可重复读（RR）：**开启事务时不会生成，只有在事务中第一次执行快照读(普通select语句)时生成，后续所有快照读复用该 Read View（保证可重复读）**；
读已提交（RC）：事务中每次执行快照读都重新生成 Read View（只能保证读已提交）；
** 核心属性（Read View 包含 4 个关键值）
|属性|	含义|
|--|--|
|m_ids|	当前活跃（未提交）的事务 ID 列表|
|min_trx_id|	m_ids中的最小事务 ID，如果m_ids列表为空，则min_trx_id等于max_trx_id|
|max_trx_id|	系统下一个要分配的事务 ID（即当前最大事务 ID+1）|
|creator_trx_id|	生成该 Read View 的事务 ID（当前事务 ID）|

**普通的select语句不会创建creator_trx_id，一个事务只有发生写操作（增删改）或者显示调用select ... for update或者select ... lock in share mode 语句才会被分配唯一的、递增的trx_id**。

因此只读事务不会有trx_id，读写事务在进行写操作才会有trx_id。


**max_trx_id 不等于 creator_trx_id +1**。举例：事务A先执行update语句生成trx_id为1,后来事务B和C执行insert语句生成trx_id为2和3并且提交，此时事务A再执行select语句创建第一个ReadView，creator_trx_id为1，但是min_trx_id等于max_trx_id为最大事务Id3+1等于4，事务B和事务C提交的内容均可见。

### 既然MVCC能解决幻读，为什么还需要间隙锁
MVCC只解决了"快照读"下的幻读，无法解决"当前读"下的幻读。为了保证数据库的一致性，所以需要有间隙锁（Gap Lock）。

**1.快照读vs当前读**

**快照读：简单的select语句。**
* 依靠MVCC：通过ReadView读取数据的历史版本
* 结果：在RR级别下，解决了幻读问题。不管别人怎么插入数据，查到的都是开启事务那一刻的快照。

**当前读：执行select ... for update、select ....lock in share mode 、update、delete、insert**

* 特点：它必须读取数据库中最新版本的数据
* 问题：只靠MVCC，当执行"当前读"的时候，新插入的数据会被看到，从而产生幻读。


**2.为什么“当前读”需要间隙锁**

想象一下这个场景：

1.事务 A 执行：UPDATE user SET salary = 10000 WHERE id > 10;

* 事务 A 的意图是：把所有 ID 大于 10 的人薪水都改了。

2. 此时 事务 B 插入了一条记录：INSERT INTO user (id, name, salary) VALUES (15, '小明', 5000); 并提交。

3.如果只有 MVCC，没有间隙锁：

* 事务 A 在更新完后，再次执行 SELECT * FROM user WHERE id > 10; (当前读)。

* 惊讶地发现： 竟然还有一个 ID 为 15 的“小明”薪水是 5000，没被改过来！

* 这就产生了幻读，且破坏了事务的原子性和一致性。

**间隙锁的作用：**
当事务 A 执行 id > 10 的更新时，InnoDB 不仅会锁住已存在的记录，还会锁住 (10, +∞) 这个间隙。此时事务 B 的插入会被阻塞，直到事务 A 提交。

**3. MVCC 无法解决的“幻读自杀”场景**

有一个非常极端的例子，证明了光有 MVCC 是不够的：

事务 A 查询：SELECT * FROM user WHERE id = 5; (返回空，因为不存在)。

事务 B 插入：INSERT INTO user (id) VALUES (5); COMMIT; (成功)。

事务 A 尝试插入：INSERT INTO user (id) VALUES (5);

报错： Duplicate key error（主键冲突）。

事务 A 再次查询：SELECT * FROM user WHERE id = 5;

结果： 依然返回空（因为 MVCC 快照读，看不到事务 B 的提交）。

此时事务 A 陷入了逻辑死循环： 查的时候说没有，写的时候说已有。这种一致性冲突只能靠间隙锁在事务 A 第一次查询（如果是加锁读）时就封锁住 id=5 的位置来解决。


**MVCC： 负责读-写并行。让普通的查询不用加锁，提高并发性能。它解决了“我读的时候，你随便改，我不受影响”的问题。**

**间隙锁 (Gap Lock)： 负责写-写”和“当前读的一致性。它解决了“我操作一个范围时，你不能往里面塞新东西”的问题。**


## 3、MVCC 的核心规则：版本可见性判断
事务通过 Read View，按以下规则判断版本链中的数据版本是否可见：假设待判断版本的DB_TRX_ID = trx_id（即修改该版本的事务 ID）：
* trx_id < min_trx_id：修改该版本的事务已提交，可见；
* trx_id >= max_trx_id：修改该版本的事务是未来事务（还未启动），不可见；
* min_trx_id ≤ trx_id < max_trx_id：
 若trx_id在m_ids中（事务未提交），不可见；
 若trx_id不在m_ids中（事务已提交），可见；
特殊情况：trx_id = creator_trx_id（当前事务自己修改的数据），可见。



**如果当前版本不可见，则通过DB_ROLL_PTR遍历版本链，直到找到第一个可见版本；若遍历完无可见版本，则返回空。**

InnoDB 的默认隔离级别（RR）是 MVCC + 间隙锁共同实现的，既保证可重复读，又解决幻读。

## 4.MVCC 与锁的关系（快照读 vs 当前读）
MVCC 仅作用于快照读（普通 SELECT），而当前读（加锁读 / 写操作）仍依赖锁机制，二者互补：
|操作类型|	依赖机制|	行为特征|
|--|--|--|
|快照读（SELECT）|	MVCC|	读历史版本，不加锁，不阻塞写|
|当前读（SELECT FOR UPDATE/INSERT/UPDATE/DELETE）|	锁（行锁 / 间隙锁）|	读最新版本，加锁，可能阻塞|

```sql
-- 快照读（MVCC）：不阻塞，读历史版本
SELECT * FROM user WHERE id=1; 

-- 当前读（锁）：读最新版本，加X锁，阻塞其他写操作
SELECT * FROM user WHERE id=1 FOR UPDATE; 
```

## 5、MVCC 的核心总结
* 本质：多版本并发控制，为每行维护版本链，通过 Read View 判断版本可见性；
* 核心组件：隐藏列（版本元数据）+ undo log（版本链）+ Read View（可见性规则）；
* 核心优势：快照读不阻塞写，写不阻塞读，提升并发性能；
* 核心作用：实现 InnoDB 的读已提交（RC）和可重复读（RR）隔离级别；
* 边界：仅作用于快照读，当前读仍依赖锁机制。

## 6.问题
### 既然MVCC能解决幻读，为什么还需要间隙锁？
**MVCC只能解决"快照读"下的幻读，而无法解决"当前读"下的幻读**，为了保证数据库的各种操作下能够维持一致，因此需要间隙锁（Gap Lock）
